# GROUP 02 — CODEGATE DATABASE FOUNDATION REPORT

## 1. Executive Summary
Group 02 establishes the parallel `codegate` package within the PR-Agent repository. The primary goal was to lay down a solid database foundation utilizing SQLAlchemy 2.x and Alembic. We defined the schema for managing Code Reviews and Pull Requests and provided basic Data Access Layer (DAL) classes without altering the core PR-Agent functionality.

## 2. Architecture Added
A new parallel package structure was introduced:
```text
codegate/
├── __init__.py
├── alembic/              # Database migration definitions
├── config/               # Settings and configuration
├── database/             # SQLAlchemy engine, session, Base, and Models
├── repositories/         # Database access layer stores (DAL)
├── schemas/              # (Reserved for Pydantic/API schemas)
└── services/             # High-level business logic
```

## 3. Dependencies Added
- `SQLAlchemy (>=2.0.0)`: Core ORM using 2.0 style features.
- `alembic (>=1.13.0)`: Schema migration manager.
- `psycopg2-binary (>=2.9.9)`: PostgreSQL adapter (usable for future production).
- `python-dotenv (>=1.0.0)`: Environment variable loading for `DATABASE_URL`.

## 4. Database Configuration
- Uses `pydantic_settings.BaseSettings` to resolve `DATABASE_URL`.
- Defaults to `sqlite:///./codegate.db` for local and testing fallback.
- `codegate/database/session.py` provides the session factory and connection parameters depending on the dialect.

## 5. Models
The following core models were successfully mapped:
- `User`: Identity details (provider, username).
- `Team` & `TeamMember`: Team structures with specific roles (Enum).
- `Repository`: Stores origin and tracking info for repositories.
- `PullRequest` & `PullRequestFile`: Details the PR and its individual file stats.
- `AnalysisRun` & `Finding`: Tracks separate analysis triggers (e.g. Webhook, Manual) and outputs generated by different tools/AI over specific commits.

## 6. Relationships
Relationships were defined using SQLAlchemy's `Mapped[List[...]] = relationship(...)`:
- `Team` -> `TeamMembers` (1:N)
- `Repository` -> `PullRequests` (1:N)
- `PullRequest` -> `PullRequestFiles` (1:N)
- `PullRequest` -> `AnalysisRuns` (1:N)
- `AnalysisRun` -> `Findings` (1:N)

*All standard "delete-orphan" cascades were applied downwards.*

## 7. Indexes & Constraints
Unique constraints added:
- `uix_team_id_user_id` (TeamMember)
- `uix_provider_full_name` (Repository)
- `uix_repository_id_number` (PullRequest)
- `uix_pull_request_id_filename` (PullRequestFile)

Performance indexes added explicitly or automatically for:
- Foreign keys (`pull_request_id`, `analysis_run_id`)
- Searching criteria (`full_name`, `head_sha`, `state`, `severity`, `source`, `status`)
